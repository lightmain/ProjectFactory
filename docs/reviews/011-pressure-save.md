### 分项计时及边界

副本停止游戏逻辑、HUD 更新、玩家物理和自动物流显示更新；
先绘制静止世界，再手动推进逻辑与刷新显示，随后绘制保留装饰的静止场景。
两次静止绘制各预热两个绘制帧，再统计 30 个实际绘制帧。
逻辑先预热 2 tick，随后分别推进两个 8 tick 批次；显示刷新传入偏移 0。
因此以下数字是同规模分项旁证，不是原 49.111435 秒长帧的精确分解：
原工具预热两次绘制、使用物理插值，物流阶段也不同。

| 阶段 | 第一轮（秒） | 第二轮（秒） |
| --- | ---: | ---: |
| 8 tick 总耗时 | 37.943565 | 41.038403 |
| 队列包装创建、遍历与引用装配 | 7.234914 | 7.616353 |
| 全图矿石位置求解 | 17.338293 | 17.267939 |
| 全设施生产检查与可交接数量更新 | 1.430307 | 1.480222 |
| 完整交接算法 | 9.752179 | 12.476113 |
| 上述分项之外的余量 | 2.187872 | 2.197776 |

队列包装计时不含函数退出时的包装销毁；完整求解和交接计时包含各自内部
暂存数组生命周期。余量含外层循环、包装销毁等未细分工作，不归到单一瓶颈。
两个批次都完成 8 tick／8 次交接，显式工作计数分别约 1.626 亿／1.677 亿次访问；
此计数不是 CPU 指令数。平均每 tick 约 4.74～5.13 秒，而 60 Hz 每 tick 预算
约 16.7 毫秒。默认 `max_physics_steps_per_frame == 8`，原窗口也实际完成
8 tick／1 绘制帧；支持一个长帧承担多次逻辑更新，不据此声称精确八倍减速。

### 原因及对照

1. **高频全图处理已确认。** [物流推进](../../scripts/core/logistics_data.gd) 每 tick
   创建每设施一份 `LogisticsOreQueue` 包装，并对全矿石求解、检查全设施生产、
   执行 [交接](../../scripts/core/logistics_batch.gd) 的多个全量循环。
   [位置求解器](../../scripts/core/belt_position_solver.gd) 还创建和处理多份逐矿石数组。
   线性复杂度测试验证访问上限，未保证百万对象在实时预算内完成。
2. **距离筛选发生过晚已确认。** `sample_belts()` 先更新全图缓存、再复制全部返回
   队列与矿石；[显示层](../../scripts/world/logistics_view.gd) 此后才检查 12 米距离。
   缓存未命中有两份矿石复制，命中仍有全量返回复制。
   此次真正提交的矿石仅 23,112 颗，约占总量 1.14%，却准备了全世界数据。
3. **装饰节点及绘制提交负担已确认。** 同一镜头下，只画静止世界为
   99.32 FPS、3,094 次绘制调用／帧、全局 6,986 个节点；加入静止装饰后为
   10.50 FPS、119,504 次调用／帧、全局 76,389 个节点。
   FPS 来自 30 帧窗口；调用数、节点数等监控值来自采样末帧，不是窗口累计或均值。
   附近有 11,561 个设施表现根；普通带的箭头与四个端口各用一个独立
   `MeshInstance3D`。矿石池已将 23,112 颗矿石装入 41 个活动批次，
   箭头和端口仍未批量表达。场景开启方向光阴影，装饰保留默认投影设置；
   尚未单独量化阴影成本。静止 FPS 包含引擎、CPU 提交、绘制与呈现，
   不能称为 GPU 独占速度；原长帧的主要 CPU 模拟成本另有上述直接计时证明。
4. **加载和网格初始化是另一组成本。** 会话文件约 11.43 MiB，解压后的 Variant
   数据为 147.31 MiB。文件读取、解压、校验和及 Variant 解析合计约 0.526 秒，
   存储层第一次完整快照解码与验证约 33.217 秒，调用方再次解码约 33.059 秒。
   `SaveGameStore._read_bank()` 和会话加载入口均调用 `SessionSnapshot.decode()`，
   造成重复世界／物流重建。场景挂载约 21.345 秒，生成 2,304 个网格／碰撞区块、
   4,164,052 个源网格三角形、12,492,156 个顶点。
   [网格层](../../scripts/world/voxel_world_view.gd) 无待更新区块时直接返回，
   这些初始化成本已排除在原 FPS 窗口之外，持续绘制成本仍存在。
5. **紧凑存档未替换运行数据模型。** 格式 4 改进序列化表示；恢复后仍使用机器、
   矿石和队列对象以及普通邻接数组。文件容量允许百万设施，并不减少逐设施、
   逐矿石模拟和复制成本；本次没有量化不同编码的总内存收益。

后续优化顺序建议：先将显示范围筛选移到全量复制／求解之前，并批量绘制箭头和
端口；物流复用队列与暂存数组，进一步采用连续数据、稳定拓扑缓存或线路段批处理。
百万规模仍需处理全图每 tick 更新的架构成本，保持 60 Hz、身份和堵塞规则时，
不能只通过缩短显示距离、降低绘制次数或修改文件限额解决。
加载可返回已验证快照以消除第二次解码，再评估按需网格／碰撞及平面合并。
这些是建议，未实施，也未宣称会达到某个目标 FPS。
