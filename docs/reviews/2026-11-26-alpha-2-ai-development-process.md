# alpha-2.0 开发过程复盘：工作量如何积累，可试玩结果为何迟迟没有形成

记录日期：2026-11-26。对象：2026-11-25 至 26 日，本次开发智能体在 ProjectFactory 中实施 Rust 数据后端迁移的过程。读者：项目开发者，以及研究 AI 软件开发效率、任务组织和人机协作的读者。

本文按用户要求记录“什么阶段在做什么功能、执行了什么操作”，并分析这次开发为何成为一个值得保留的反例。本文是有日期和范围的过程记录，不取代版本规格，也不证明当前工作树已经完成迁移。

**本次确实实现了世界、工厂规则、同步试玩、存读档，以及大量后台通信和静态表现组件。但开发智能体把工作拆成了过多的组件交付循环，前期投入了超出实际玩法需要的数值边界验证，后期又出现接口误用、错误测试假设和反复收尾。用户等待的完整后台试玩一直没有形成。降低测试频率的要求后来确实执行了，但批次组织仍未充分转向可直接体验的结果。**

这不是一个可以简单归结为“测试太慢”的案例。测试执行、编译、准备隔离项目、分析失败、修复实现、修正测试、独立审查、维护规格、重新验证，都在发生。现有证据可以还原这些动作及其先后关系，但不能把全部等待时间精确分摊到每一类动作。

## 2. 用户最初要迁移什么

ProjectFactory 是一个 Godot 三维体素工厂游戏。迁移开始前，Godot 脚本保存方块、机器、库存和模拟时间，也处理生产、拓扑和存档。Godot 还负责玩家输入、镜头、网格和物理碰撞。

项目已经接入独立的 RustConveyor 包作为可选连续运输后端。RustConveyor 管理运输段、矿石队列、合流分流、预订和预测；这不意味着整座工厂已经由 Rust 管理。原先 Godot 仍须决定设备生产、给运输提供输入，并处理接收库存。

alpha-2.0 的目标是把**完整数据状态和规则执行**迁入 Rust。Rust 世界线程独占方块、机器、库存、运输和模拟时间；Godot 负责输入、显示和引擎碰撞。磁盘读写另由 I/O 工作线程执行。这里的“世界线程”是在同一应用中的后台线程，并不是另行部署的网络服务器。

这项迁移涉及的操作有一个根本变化。同步代码调用“放一个方块”后，可以立即读取结果。后台代码先提交请求，稍后才能领取结果；领取时，玩家可能已经移动，显示订阅可能变化，甚至活动世界已经换成另一个存档。实现必须识别迟到的结果，也必须保证重要操作不会因队列满而丢失。

几项后文反复出现的概念如下：

| 名称 | 它表示什么 | 为什么需要 |
| --- | --- | --- |
| `world_epoch` | 一次活动世界实例的代号 | 防止旧世界结果应用到新世界 |
| `world_revision` | 世界编辑修订 | 判断预览、网格和碰撞是否仍对应当前状态 |
| `command_seq` | 请求的递增序号 | 同一个请求重发时只执行一次 |
| `result_seq` | 可靠结果的发布序号 | 按连续消费水位确认结果，不被较早的长作业阻挡 |
| ACK | 调用方确认已处理某份结果 | 后端在确认前保留数据，确认后才释放额度 |
| `Busy` | 此刻无法接收或领取 | 队列满或短锁竞争时立即返回，调用方保留原请求重试 |
| 候选世界 | 从存档恢复、尚未换入的独立工厂 | 坏档、取消或表现准备失败时保留原活动世界 |
| oracle 对照 | 由已有实现独立生成观测，再与新实现比较 | 为迁移提供参照；对照通过本身不证明参照玩法成熟 |
| RED / GREEN | 先确认验收失败，再实现到验收通过 | 区分未实现接口、真实行为缺陷和错误测试夹具 |

最初计划从 M00 基线测量到 M15 默认切换，完整范围见[迁移计划](../features/alpha-2.0/003-migration-plan.md)。因此，这不是只改一条折线算法的任务。不过，范围大也不能自动解释每一轮重复工作为什么必要。

## 4. 初始材料与 M00：先测基线，随后修测量工具

### 4.1 初始材料保存

开发智能体读取规则、README 和三份规格，查询 Git 分支及未提交文件，随后在 `feat/alpha-2.0-rust-backend` 开发。用户授权后，提交 `4f1fee4`，保存三份 alpha 规格、独立静态 Rust 世界原型、原型测量和分享包。

提交前执行了完整 Godot 验证，以及原型的格式、测试、Clippy、release 构建和 Python 工具检查。两个独立审查者分别核对规格与分享包、原型。该提交只保存起始材料，没有把完整 Rust 后端交付为成品；当次记录为未推送。

### 4.2 为什么 M00 先改 Python 和 Shell

M00 要测旧工厂的构建、保存、独立读档、挂载和运行成本。原采集器缺少可靠的超时及 RSS 停止记录。RSS 是进程驻留内存，本次采用定期观测后停止进程的方式，不是操作系统硬配额。

开发智能体先修改验收，确认旧工具会失败，再修改 `scripts/pressure_phases.py`、压力包装脚本和报告检查器。新增行为包括：非法限额在进程启动前拒绝；观测超限后停止；保留已经采到的阶段和内存样本；失败例不进入有效性能比较。

独立审查发现三项实际缺口：验证副本没复制新测试；进程在观测超限后刚好退出，工具漏记失败；检查器允许限额和样本相矛盾。开发智能体逐项补复现、修复并复验，再执行完整 `verify.sh`，451 项 GdUnit4 测试及相关检查通过。

这段工作产出的是可信测量工具。它没有推进新后端玩法，但避免了把失败测量当成成功性能数据。

### 4.3 执行了哪些测量

最初的小型工厂有 1,124 条带、4 台矿机、1 个箱子；复杂工厂有 34 条带、3 台矿机、4 个箱子，含环路和合流。两规则集各生成存读档一次，再各用三个独立进程加载，共 16 次成功进程。

随后完成 48 个成功无头进程，覆盖两规则集的小型、复杂、万级、十万级，分别取得三轮生成存读档和三轮独立加载。加载轮次包含三次异世界保存和切换。每个采样过程预热 120 tick，再测 300 tick。

图形批次另有 48 个成功独立进程，覆盖两规则集、四类场景、固定和移动视角各三轮。中断记录保留，补跑使用新编号。16 个图形组中有两个组的窗口焦点条件不同，被标为条件不匹配，没有为了消除这个限制继续补跑。

百万工厂第一次在约 1 GiB 停止线下构建失败；后续仅提高一次至 4 GiB，再次失败后没有继续提高。两规则集后续观测峰值分别约为 4.32 和 4.60 GB，仍在构建阶段停止，未完成保存、加载和挂载。

**这些是旧工厂基线测量，不是新 Rust 世界已经接入后的百万失败。** 初始 16 次成功与后续两组 48 次成功是不同批次，不能据此推算完整工具次数或开发耗时比例。基线同时还缺玩家真实首次输入和碰撞可操作证据，因此 M00 整体没有被关闭。[来源：E1、E2](#e1)

### 4.4 这一阶段的组织成本

为减少污染基线，测量按顺序运行；M01 的代码准备和只读审查可以穿插，但新编译、测试和额外引擎进程等待测量结束。新增 Rust workspace 后，开发智能体又修正验证副本，避免复制 `rust/target` 编译产物。

这些约束有明确测量理由。不过，用户最早等待的成果中，已有相当一部分是“测量是否可信”和“验证是否隔离”，而非可操作的迁移场景。后续进度说明需要把两者分开，不能都称为“后端开发已推进”。

## 5. M01：建立 workspace、桥接和旧档输入

开发智能体建立三个 crate：`factory_core` 管理纯 Rust 规则，`factory_cli` 提供命令行验收，`factory_godot` 负责 GDExtension 桥接。核心和 CLI 不依赖 Godot；最初扩展只允许握手和关闭，不创建世界或线程。

先运行缺接口的失败验收：核心缺 `protocol`，CLI 无输出且非法命令返回成功，安装器缺 `build.py`，黄金档缺 manifest；Godot 专用入口缺库时明确退出，没有回退旧脚本。

随后实现安装器、能力握手、构建身份、许可归档和格式 1～4 的黄金输入。构建身份记录实际源码、锁文件、工具链和编译参数；黄金输入由旧 Godot 写端在隔离目录生成，不读取玩家个人存档。

这一阶段有三类返工：

1. **实现边界写错。** 首次编译遇到 gdext 宏注册的 unsafe 边界，以及 PackedArray、Dictionary 参数必须传引用的问题。开发智能体按实际 API 修正，未全局放宽检查。
2. **验收本身不充分或假设错误。** 审查要求绑定清单标签与真实字节、防止两端停摆仍相等、保存语义坏档、补 typed Variant 和时间边界。读回过程又遇到 JSON 数字类型与原整数不同、Godot 版本字符串格式不同、连续矿石不能只统计机器 quantity 等问题。
3. **首次发现扩展时的引擎退出异常。** 新扩展首次立即导入退出出现 signal 11，随后 crash handler 使进程以 -6 退出；原 RustConveyor 也复现，无扩展对照正常。换渲染器和只等 10 帧没解决。先运行无头编辑器 120 帧、限制 60 FPS 后，正常退出及后续导入通过。记录将其限定为兼容处理，没有宣称找到引擎根因。

安装审查还发现 `native` 父目录符号链接可能把安装重定向到项目外。开发智能体增加无编译复现，修正前后目录校验，七项安装测试通过，再独立复审。

最终生成 12 个旧档案例和 8 个拒绝输入，字节核对及跨进程继续演化通过。独立探针还执行 4,092 个截断、版本、计数和尾字节变异并拒绝。M01 在完整验证和复审后闭环。

本阶段留下的 PackedArray 引用问题很关键：它已经成为可获得的经验，但最新查询桥接又发生同类误用。后一次不应再次解释成完全陌生的环境问题。[来源：E1](#e1)

## 6. M02：有限世界、结构占用和检查点

开发智能体把准备测试注册到 `factory_core/tests/world.rs`，实际确认缺 `world` 模块，再实现 `world.rs`、`entities.rs`。

世界使用隐式平地和 32³ 编辑区块：未编辑地形不逐格生成对象；修改时分配稠密方块页。结构保存实例身份及占用索引，挖掘任意占用格可以拆整座结构。只读克隆共享方块页，但当时仍复制实体和占用表。

首批 11 项测试通过后，继续增加差量恢复、重复记录和漏 owner 拒绝、边界吸附、绝对坡面高度等验收，实际确认缺少相应 API 再实现。最终 19 项世界验收通过，包括百万带、4,096 座结构的 110,592 个占用格。

验收覆盖帧重发、跳帧、正时间暂停拒绝、恢复、delta 0 姿态、tick 和非默认完整玩家字段。执行中的时间事件继续计入积压，完成才释放额度；已接收时间失败时冻结剩余时间流。

两结果额度下真实触发 Busy，再 ACK、退休、重试，将后台完整存档字节和账目与同步事件流比较。针对性测试、独立审查、完整 Rust 和 464 项 Godot 检查通过。单事件最多五 tick 只限制规则步数，不等价于固定墙钟耗时。

### 11.3 M06c-1：关闭和真实线程回收

给存档 Service 和世界 runtime 增加非阻塞关闭、拒绝新任务及真实退出查询。工作线程由额外 owner 线程 join，退出通知在工作线程清理完成后发布；Godot 主线程不 join。

已进入 Committing 的保存继续返回真实结果，不能因关闭把可能已提交的文件删除。测试覆盖重复关闭、取消、提交不确定和目录重开。线程析构用有界通道暂停，确认清理和 join 前不能报告退出。

独审保留两项覆盖建议，特别说明“已经观察到提交状态”并不证明关闭一定与磁盘提交重叠。针对性、完整 Rust 和 464 项 Godot 回归通过。

### 11.4 M06c-2a：世界内保存及取消

把有序 Save 接到世界线程，在事件边界捕获工厂和完整玩家帧，再交子 I/O。保存槽位一直占用到终态消费；取消使用独立控制预算，不能把普通保存提前退休。

实际 I/O 在 Encoding、Committing 阶段设可控屏障，验证取消先胜和提交先胜；同时后续世界查询可正常发布。关闭或世界 panic 需等子 I/O 真正回收。

审查和复审引出三次修复：I/O panic 被报为非法输入，新增 WorkerFault；捕获完成后未检查关闭就派发新 I/O，增加前后检查；请求接收端已断开却被当 Busy，区分 Full 和 Disconnected。

最终针对性覆盖 27 项库测试及通道、时间、保存、I/O 回归，Clippy 和完整 Rust 通过。旧记录中多次保留“Godot 全量待通知”，不能把同一待完成批次在每片都当成新一次通过。

### 11.5 M06c-2b-1：目录分页与独立 ACK

目录终态只含身份、序列和条数，实际元数据另保留分页载荷。终态 ACK 与载荷 ACK 分开，任意次序都不能释放错目录。保留旧目录时允许保存新档，旧快照不能跟着改变。

实际临时目录、Reading 屏障、错误身份、字节不足、取消、关闭和 I/O panic 都有验收。补 65 条目录及长 emoji 名称的边界分页，直接测试精确字节和少一字节。针对性、独审、Clippy 和完整 Rust 通过；最后新增边界测试由针对性覆盖，没有假称全部在先前全量中执行。

### 11.6 M06c-2b-2：后台候选恢复

## 15. 这个反例可以分析什么

### 15.1 数值正确性变成了持续升级的交付条件

**观察：** M03 至少八轮编号复审，输入从普通射线走到极大指数、极小 subnormal 和精确有理数。用户排除后，15 项极端测试、精确路径及依赖被删除。

**分析：** 独立审查在其给定范围内找到了真实问题，但执行者没有及时判断这些问题与玩家有限世界中的正常目标是否匹配。每次发现都转成阻断，使前一个修复又成为后一轮更极端探针的起点。

这支持“验收边界没有及时收敛”的判断。它不支持“所有边界测试都无价值”：oracle 输入绑定、普通格面、迟到障碍、账目和坏档保护仍有直接用途。

### 15.2 完整验证启动时机造成重复劳动

**观察：** 多次完整 Rust/Godot 批次在独审尚未结束时启动，又因审查修复或新增验收被主动停止。部分先通过结果对应修复前源码。

**分析：** 停止旧批次避免了错误声称最终源码通过；但前面的工作安排让构建、安装、导入和对照提前付费，修改后再付一次。损耗来自执行顺序，而非只来自单个测试用例耗时。

后期复用同库补未执行尾部，是已经实际发生的改进。不能把前期做法无区别地套到降低频率后的每个批次。

### 15.3 组件通过数量没有对应到玩家可用进展

**观察：** 通道、时间、生命周期、保存、目录、候选、切换、桥接、宿主、CPU 网格、分页、安装、领取、交接都分别有验收与文档，而能力声明和主场景仍未启用完整后台路径。

**分析：** 每个组件有局部正确性，却只有在输入、规则、查询、显示和碰撞连通后才能变成玩家的一次完整操作。按组件不断收尾，会产生很多可报告成果，同时把系统集成留到后面。

用户看到的是长时间等待之后仍需“下一批接真实场景”。这与局部代码是否有产出并不矛盾，反映的是阶段划分没有充分以产品结果为单位。

### 15.4 测试也会错，AI 会制造新的验证成本

**观察：** 连续矿石计数漏 checkpoint；CUSTOM0 类型判断错误；遮挡底面期待错误；低箱子被当不可跨障碍；非设备被传设备方向；测试作用域插错；一次 Busy 被期待成非法参数。实现还发生 Option 类型错误、gdext 注册误用和重复 PackedArray 引用错误。

**分析：** 失败输出既可能指出实现错误，也可能指出验收或编排错误。执行者必须先判断失败类别。若把每次失败都视为游戏复杂性，错误测试会反过来驱动错误实现。

最新箱子案例中，开发智能体最终保留合法爬坡规则并修测试，这是正确处理；写出错误假设并额外重跑则属于作者可避免的损耗。

### 15.5 自动验收侧重低层，普通体验仍有遗漏

**观察：** 第一版试玩在自动验收和截图检查通过后，玩家马上发现 UI 缺失和单次编辑重建 873 格。后续中心线转弯问题也由用户具体反馈推动补全。

**分析：** 低层大样本对照不能替代连续操作和既有体验检查。首版没有足够早地验收界面复用、局部编辑资源保持和矿石转弯连续性，使修复在交付后发生。

这支持提前安排普通玩法完整链路的必要性，不能推出低层测试应全部删除。

### 15.6 耗时说明一度用局部时长替代整段过程

**观察：** 14:41 的回应强调 464 项测试约三分钟，用户 14:42 指出已经等待三小时。同轮回应即承认解释不准确，指出重复批次和执行组织问题；14:45 再详细说明桥接工作、epoch 修复和尚未启动 3b。20:18 又必须澄清降低频率有执行但不充分。

**分析：** 用户问的是这一段时间完成了什么、为什么迟迟没有可用结果。单次测试时长只能解释某一步等待。用它解释整体，会遗漏编码、编译、隔离项目、失败分析、修复和审查，也会掩盖阶段目标仍未达成。

现有证据不能给出精确三小时分配。更诚实的回答是动作台账、已完成链路、尚未完成链路，以及哪些返工属于作者错误。

### 15.7 用户承担了重复纠偏和产品发现成本

**观察：** 用户先缩减极端验收，再催复用现有库、修正常体验、询问全计划状态、要求降低频率，最后再次询问该要求是否执行。

**分析：** 执行者虽然自主完成了许多局部工作，却没有持续把这些偏好转成明确批次边界和可见验收。用户不得不重复判断重点、推动集成和核对进度。

这次案例能够证明本次执行中的组织与沟通问题，不能从一个样本推断所有 AI 开发系统的平均效率，也不能据此给出同等人类工程师一定需要多久。

## 16. 针对本次问题，可以怎样改变后续工作

以下是复盘得出的建议，不是本文已经执行的游戏改动，也不是重新征求用户授权。

1. **以完整普通操作定义阶段。** 例如一个阶段结束必须在真实场景中完成后台移动、射线瞄准、线路预览、建拆、画面与碰撞更新、暂停恢复。组件检查点仍保留，但不逐个当成产品交付。
2. **先稳定一批接口和实现，再做独审和阶段全量。** 日常只运行受影响模块；独审阻断集中修复；修复后做针对性复验，达到阶段边界才跑完整入口。避免审查尚未返回就预先启动昂贵全量。
3. **落实用户已排除的范围。** 人工数值极限不再自动升级为阻断；正常流程、数据一致性和坏档保护仍保留。后续审查任务应明确该边界，避免换一轮审查又恢复旧标准。
4. **编写桥接前核对现有 API 和相邻用法。** gdext 注册、PackedArray 引用和真实类型应从已成功代码复用。测试夹具先确认路线能否爬坡、实际数组类型和非阻塞 Busy 语义。
5. **尽早核对普通体验。** 局部编辑保留显示资源、工具栏和菜单连续性、转弯矿石轨迹，都应进入第一条可运行链路，而非等玩家交付后报告。
6. **让每次运行证据能追溯到源码快照。** 每轮日志用独立名称，保留首个错误及周边输出；记录构建指纹。验证在后台时继续修改源码，必须明确哪一轮对应哪一份代码。
7. **状态回复先说能用什么。** 如“同步试玩可用，后台查询未过桥，后台动态显示未接”，然后才列组件和测试。被问状态时及时给完整短答，不继续展开新开发批次。

本次后期已经做到集中相关测试、阶段检查、复用同库补尾部、窄范围复审。真正还需要改变的是，把这些动作服务于一个更大的可试玩阶段，并减少本可避免的接口和夹具返工。
